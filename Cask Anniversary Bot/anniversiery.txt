Freelancer Brief — Weekly "Cask Anniversary" Zap
Zapier + HubSpot + Gmail
Project type: One-off Zapier build
Estimated effort: 4–6 hours for an experienced Zapier developer

About us
London Cask Traders is a UK-based whisky cask brokerage. We use HubSpot as our CRM and Gmail for email. Every week we want our brokers to receive a briefing of which clients are hitting cask-purchase anniversaries that week, so the broker can call them for a relationship check-in.
This brief is for building one scheduled Zap that automates the briefing.


What we want built
A single Zap, scheduled to run every Monday at 08:00 Europe/London, that does the following:
Looks at all closed-won deals in HubSpot
Identifies any deal whose closedate falls on the same calendar date in any prior year, within a 7-day forward window from today
Groups results by the deal owner (the broker)
Sends each of 5 named brokers an HTML email listing their clients whose anniversaries fall in the coming week
Sends a manager (Oliver) one summary email covering all anniversaries across the team
The output format is already designed and tested — see "Output format" below. You do not need to design the email; just build the Zap that produces it.


Critical detail: the date logic
This is the only non-trivial part of the build and the most common source of mistakes.
For today's date T, the Zap must find every closed-won deal where:
closedate.month-day is between T.month-day and (T + 7 days).month-day
AND closedate.year < T.year
In plain English: "If today is Monday 26 April 2026, find all deals that closed on 26 April – 3 May in any year before 2026."
HubSpot's native "Find Deal" Zapier action does not support this filter directly. You have two viable approaches:
Approach A (recommended): Use a Code by Zapier step that calls HubSpot's CRM Search API directly with a filterGroups payload that includes one filter group per prior year (we expect to look back at minimum 5 years, so 5 filter groups). HubSpot's CRM Search API supports BETWEEN operators on date properties.
Approach B: Pull a wider set of deals (e.g. all closed-won deals from the last 6 years) and filter in JavaScript in a Code step. Simpler logic but pulls more data.
Either is acceptable. Approach A is cleaner and faster.

Critical data quality issue
The HubSpot deal data has known duplicates. Many casks (e.g. cask reference 877361) appear as 2–4 separate deal records. The Zap must de-duplicate before producing emails, otherwise clients get listed multiple times.
De-duplication rule: Each deal name follows the pattern [Distillery] Cask ([Description]) — [6-digit reference]. Parse the trailing 6-digit reference and treat that as the unique cask identifier. Keep one record per cask reference (use the highest amount to break ties).
Example deal names:
Bunnahabhain Cask (200L Ex-Bourbon Barrel) — 877351
Glenrothes Cask (250L Hogshead Ex-Bourbon Barrel) — 877352
Crabbie Bonnington Cask (200L Ex-Bourbon Barrel) — 877362
Regex suggestion: /—\s*(\d{6})\s*$/ to extract the reference.


Joining deals to contacts
Each deal in HubSpot has associated contacts. The email needs to list the client name (from the contact), not the deal name. For each de-duplicated deal:
Look up associated contacts via the HubSpot API (/crm/v3/objects/deals/{dealId}/associations/contacts)
Take the primary contact (or first if there's only one)
Pull firstname, lastname, phone, and the contact's HubSpot ID
The contact's HubSpot ID is needed to construct a clickable link to their CRM record. The link format is:
https://app.hubspot.com/contacts/25187088/record/0-1/{contactId}
If a deal has no associated contact, list the cask reference and mark it as "contact lookup needed" rather than failing the whole run.
⚠ CRITICAL — Pagination on the associations lookup
This is the #1 mistake we've seen on this build. The HubSpot /crm/v3/objects/deals/{dealId}/associations/contacts endpoint and the search-with-associations endpoints both paginate by default at 100 records per page. If you query associated contacts for the whole batch of weekly deals in one call, you may silently get back fewer contacts than there actually are, with no error and no obvious truncation indicator. Some clients will appear missing when they aren't.
Required handling:
Always check the paging.next.after cursor in the response and follow it until exhausted
Or query each deal's associated contacts individually (slower but safer)
Add an assertion: if total in the response is greater than results.length, log a warning and paginate
Test with a deal that has 5+ associated contacts to make sure your handler returns all of them
We've already validated the test data: when querying associations for the full set of ~30 unique anniversary casks in a single call, the response caps at 45 contacts. The actual count is higher. Build for this.

Things to test for and watch out for
These are the gotchas that have caught us out already:
The associations API paginates silently. Already covered above, but worth repeating: this is the most likely failure mode. A response of 45 contacts when 50 exist returns no error. Always paginate or batch-per-deal.
HubSpot stores closedate as ISO 8601 with a 23:00:00Z timestamp (UK time offset). Match by date, not by full timestamp.
Date arithmetic across year boundaries: if the Zap runs on, say, 30 December and looks 7 days forward, it will need to query both December and January in prior years. Not relevant for most weeks but worth handling.
Gmail's API silently drops emails when the auth token is stale. Add an error notification — if a Gmail send fails, send a failure alert to oliver@londoncasktraders.com via a backup channel (or surface in Zapier's task history).
HubSpot rate limits: if pulling associations for 30+ deals one by one, batch where possible. The CRM Batch API supports up to 100 reads per call.
Some deals have no hubspot_owner_id: route these to the manager's data-quality flag list rather than dropping them.
One specific deal (Auchentoshan, ref 878988) currently has no owner — confirm it shows up in the data quality flags on the first run.
