# Automated Daily Pipeline Briefing Emails — Handover & Setup Guide
**Client:** London Cask Traders
**Platform:** n8n (two workflows + one Data Table)

---

## 1. Overview

Every weekday morning, this automation does what the sales manager previously did by hand: it produces a personalised pipeline briefing email for each Account Manager, then emails it to them, and finally reports back to the manager on whether the run completed cleanly.

For each Account Manager, the system pulls **live HubSpot data** and assembles a single AI-written email covering:

- Their month-to-date closed-won revenue and how it tracks against the £35,000 monthly target.
- Today's top priority calls (their highest-value open deals).
- Stale deals that need attention (overdue close dates, or no contact in 60+ days).
- Uncontacted leads (contacts assigned to them that have never been contacted).

The email body is generated by Anthropic's Claude model (via OpenRouter) as ready-to-send HTML, then delivered through Gmail. No manual work is required on any given day — reps are pulled live from HubSpot, so adding or removing a team member changes the recipient list automatically on the next run.

The whole system is two n8n workflows backed by one n8n Data Table that acts as a daily run log.

---

## 2. How It Runs

Two scheduled workflows run back-to-back each weekday, both on **Europe/London** time:

| Time | Workflow | What it does |
|------|----------|--------------|
| **07:30 Mon–Fri** | **[Flow 01] – Send Daily Account Manager Briefings** | Builds and sends one briefing email per Account Manager. |
| **07:50 Mon–Fri** | **[Flow 02] – Send Manager Daily Run Summary** | Reads the run log and emails the manager a pass/fail summary. |

> **Timezone note:** the schedule triggers themselves do not set a timezone on the node, so they use the n8n instance/workspace default. The workspace default is confirmed as Europe/London, and Flow 01's date calculations (days-left-in-month) explicitly use Europe/London. **Before go-live, confirm each workflow's Settings → Timezone is set to Europe/London** so the 07:30 / 07:50 fire times and the run-log dates all line up.

### The Data Table

Both flows share an n8n Data Table named **Briefing Run Log** (`dataTableId 8HZDLdL9gQUDwETS`). Flow 01 **writes** to it (one row per rep per day, tracking progress); Flow 02 **reads** from it to decide what to tell the manager. The 20-minute gap between the two flows gives Flow 01 time to finish before the manager summary is sent.

## 3. Flow 01 Walkthrough — Send Daily Account Manager Briefings

The nodes group into five logical stages.

### Stage A — Find today's Account Managers
1. **Start Weekday Briefing** (Schedule Trigger) — fires at 07:30 Mon–Fri (cron `30 7 * * 1-5`).
2. **Test Mode** (Set node) — runs immediately after the trigger and sets a single run-wide Boolean field `TEST_MODE`. This is the master switch that decides where every email goes (see §6 — Toggle test mode). It does not affect the data pulled, only the final recipient.
3. **Get HubSpot Owners** (HTTP Request) — `GET /crm/v3/owners` (limit 100) returns the full owner roster with team memberships.
4. **Split Owners List** — splits the API `results` array into one item per owner.
5. **Filter Account Managers** (Code) — keeps only owners whose team memberships include one of the briefing recipient teams (**163861030** Account Managers, **180708927** Mid Sales, **180708902** Top Sales, **167787456** Loaders / Repeat Business Reps) and reduces each to a slim object: `ownerId`, `firstName`, `lastName`, `email`. One item per rep flows onward, so the rest of the workflow loops automatically.

### Stage B — Idempotency gate (don't email the same rep twice today)
6. **Check Not Done Today** (Data Table, `rowNotExists`) — passes a rep forward only if no row in Briefing Run Log already has that `owner_id` + today's `run_date` + status `done`. This makes the workflow safe to re-run.
7. **Mark Rep In Progress** (Data Table, `upsert`) — writes/updates the rep's row with status `in_progress` before any processing begins, so failures are visible later. Its output (the table row) is what feeds the loop, so each loop item carries snake_case columns (`owner_id`, `rep_name`, `email`, `run_date`, `status`).
8. **Loop Over Reps** (Split In Batches) — processes reps one at a time.

### Stage C — Pull this rep's HubSpot data
9. **Get Open Deals** (HTTP Request) — `POST /crm/v3/objects/deals/search` for the rep's open deals (`hs_is_closed = false`), sorted by amount descending, limit 100.
10. **Build Deal Buckets** (Code) — splits open deals into **priority calls** (top 5 by value) and **stale deals** (close date in the past, or last-contacted older than 60 days; top 10 by value). Builds a HubSpot record link per deal.
11. **Get Uncontacted Leads** (HTTP Request) — `POST /crm/v3/objects/contacts/search` for the rep's contacts that have never been contacted (`notes_last_contacted NOT_HAS_PROPERTY`), newest first, limit 15.
12. **Shape Uncontacted Leads** (Code) — normalises each contact into `contactId`, `name`, `phone`, `assignmentAgeDays`, `createdate`, and a HubSpot record link.
13. **Get MTD Closed Won** (HTTP Request) — `POST /crm/v3/objects/deals/search` for the rep's month-to-date closed-won deals (stage ids `2563529956`, `2601372909`, `closedwon`) within the current calendar month. The close-date window is computed dynamically from `$now.setZone('Europe/London')` (`startOf('month')` to `endOf('month')`), so it advances automatically each month.

### Stage D — Generate and send the email
14. **Build Claude Payload** (Code) — assembles the final per-rep JSON: `rep` (`ownerId`, `fullname`, `firstName`, `email` — `firstName` is the first word of `rep_name`, used for the greeting), priority calls, stale deals, uncontacted leads, MTD closed-won total, `percentOfTarget` (against the £35,000 target), and `daysLeft` in the month (Europe/London).
15. **AI Agent** + **OpenRouter Chat Model** — Claude generates the raw HTML email body. The prompt defines the exact section order, money/colour formatting, empty-state handling, and the sign-off ("Have a strong day." / "Kind regards,"). Model: `anthropic/claude-sonnet-4.6`.
16. **Send a message** (Gmail) — emails the HTML body. The recipient is chosen by the test-mode switch: `sendTo` is an expression that returns the manager's address when `TEST_MODE` is true, otherwise the rep's own address (`$('Build Claude Payload').item.json.rep.email`). Subject: `Your daily pipeline briefing - {{ $now.format('cccc d MMMM') }}`.

### Stage E — Mark done and loop
17. **Mark Rep Done** (Data Table, `update`) — sets the rep's row to status `done`.
18. **No Operation, do nothing** — passes control back to **Loop Over Reps** to fetch the next rep.

## 4. Flow 02 Walkthrough — Send Manager Daily Run Summary

A simple linear chain of four nodes.

1. **Start Manager Summary** (Schedule Trigger) — fires at 07:50 Mon–Fri (cron `50 7 * * 1-5`).
2. **Get Daily Run Log** (Data Table, `get`) — reads every Briefing Run Log row for today (filter: `run_date = today`, returns all).
3. **Build Manager Summary** (Code) — splits the rows into **done** (`status === 'done'`) vs **pending** (anything else):
   - If all reps are done → success email, subject **"Daily briefing run complete"**, listing every briefed Account Manager.
   - If any are still pending → action-needed email, subject **"Action needed - N briefing(s) did not complete"**, listing both Sent and Not-completed reps (with a red alert box).
4. **Send Summary (Gmail)** — sends the summary to **oliver@londoncasktraders.com**.

The flow always sends one email per run; only the subject and contents change based on whether everything completed.

## 5. The Briefing Run Log Table

A single n8n Data Table (`8HZDLdL9gQUDwETS`) does three jobs at once:

- **Success log** — a record of which reps were briefed today.
- **Rerun guard** — if the workflow is re-run, reps already marked `done` today are skipped, so no one gets a duplicate email.
- **Failure detector** — any row left at `in_progress` (never reached `done`) tells Flow 02 that rep's briefing did not complete.

**Columns** (all text): `email`, `owner_id`, `rep_name`, `run_date`, `status`.

**`run_date` format:** every node writes and reads the date as `{{ $now.format('cccc d MMMM') }}` — e.g. `"Friday 12 June"`. All five table operations use this identical expression, so they always match each other within a day. (Note: this string has no year, so the dedupe is exact-match on weekday + day + month.)

**Status lifecycle for each rep, per day:**
1. **Skip-if-done** — Flow 01 checks no `done` row exists for today before starting.
2. **Upsert `in_progress`** — written before the rep's data is pulled.
3. **Mark `done`** — written after the email is sent successfully.

## 6. Configuration Guide

Each change below names the exact node and field to edit.

### Change the monthly revenue target
- **Primary:** `Build Claude Payload` (Code node) → `const MONTHLY_TARGET = 35000`. This drives `percentOfTarget`.
- **Also update:** the `AI Agent` prompt text references `target.monthlyTarget = 35000` and the colour thresholds. Update both so the email copy and the underlying number stay in sync.

### Edit the email structure or Claude prompt
- **Node:** `AI Agent` → prompt (`promptType = define`).
- The prompt controls section order (greeting → monthly target block → priority calls → stale deals → uncontacted leads → reminders → sign-off), the money/colour formatting rules, empty-state handling, and the raw-HTML output requirement.
- **Colour thresholds** (target block): `percentOfTarget >= 90` green, `50–89` amber, `< 50` red. Callout colours: green `#2e7d32/#edf7ed`, amber `#ed6c02/#fff4e5`, red `#d32f2f/#fdecea`.
- **Sign-off** is the literal text `Have a strong day.` then `Kind regards,`. Note: Gmail's web signature does **not** auto-append on API sends, so any signature must be baked into the email HTML.

### Change the included HubSpot teams
- **Node:** `Filter Account Managers` (Code) → keep the included team IDs in one list:

  ```js
  const ACCOUNT_MANAGER_TEAM_IDS = [
    "163861030", // Account Managers
    "180708927", // Mid Sales
    "180708902", // Top Sales
    "167787456", // Loaders (Repeat Business Reps)
  ];
  ```

- Add or remove HubSpot team IDs in this list when the briefing recipient group changes.

### Toggle test mode (divert all emails to the manager)
- **Implemented.** The master switch is the **Test Mode** node (a Set node) that runs immediately after the trigger. It holds one Boolean field, `TEST_MODE`.
  - `TEST_MODE = true` → every rep's briefing is sent to the manager's inbox (`oliver@londoncasktraders.com`) for safe testing. No real rep receives anything.
  - `TEST_MODE = false` → each briefing goes to the rep's own address. **This is the go-live setting.**
- **To flip it:** open the **Test Mode** node and toggle the `TEST_MODE` value between `true` and `false`. That is the only change required.
- **How it works:** the `Send a message` (Gmail) node's `sendTo` field is the expression
  `={{ $('Test Mode').first().json.TEST_MODE ? 'oliver@londoncasktraders.com' : $('Build Claude Payload').item.json.rep.email }}`.
  When true it returns the manager's address; when false it returns the rep's address.
- **Important — keep `TEST_MODE` a Boolean.** In the Test Mode node the field type must be **Boolean** (not text). A text value of `"false"` is still truthy in n8n and would silently keep you in test mode. To change the test destination, edit the manager address inside the `sendTo` expression.
- **Optional:** to tag test emails for easy filtering, prefix the subject with the same switch: `={{ $('Test Mode').first().json.TEST_MODE ? '[TEST] ' : '' }}Your daily pipeline briefing - {{ $now.format('cccc d MMMM') }}`.

### Change the Claude model
- **Node:** `OpenRouter Chat Model` → `model`. Currently `anthropic/claude-sonnet-4.6`.
- **Important:** the brief specifies `claude-sonnet-4-7`, which is **not a valid model ID and will 404**. The flow correctly uses `anthropic/claude-sonnet-4.6` (the current Sonnet via OpenRouter). Keep it on `claude-sonnet-4.6` unless you deliberately move to a newer model.

### View the run log (logs)
- Open the **Briefing Run Log** Data Table (`8HZDLdL9gQUDwETS`, project `whUv9Mwz7WJ7hkC5`) in n8n. Each row shows `rep_name`, `email`, `run_date`, and `status`. Rows stuck at `in_progress` are the ones that failed that day.
- For execution-level detail (errors, API responses), use n8n's **Executions** view for each workflow.

## 7. Error Handling and Reruns

This system uses a **stop-on-error + status-table rerun** model, which is a deliberate deviation from the brief (see §8):

- Each rep is marked `in_progress` up front and only flipped to `done` after their email sends.
- If HubSpot or Claude fails for a rep, that rep's row stays at `in_progress`. The workflow does not send a per-rep failure email to the manager; instead, **Flow 02 surfaces the incomplete reps** in the 07:50 summary ("Action needed — N briefing(s) did not complete").

**To recover a failed run:**
1. Identify the failed reps — they are the rows still at `in_progress` in the Briefing Run Log for today (and they appear in Flow 02's action-needed email).
2. Fix the underlying cause (usually a transient HubSpot/Claude/OpenRouter API issue).
3. **Re-run Flow 01.** The `Check Not Done Today` gate skips every rep already at `done`, so only the failed reps are reprocessed — no duplicate emails go out.

## 8. Known Deviations from the Brief

Please review and sign off on these:

1. **Error handling model.** The brief asked for "continue with the others + a per-rep failure email to the manager." We instead use stop-on-error with the status table as the audit trail and rerun guard, and Flow 02 reports incomplete reps to the manager at 07:50. Rationale: failures are almost always transient external-API issues for the developer to fix (not the manager), reruns are safe because `done` reps are skipped, and the manager still gets visibility into what didn't complete.

2. **Claude model ID.** The brief's `claude-sonnet-4-7` is not a real model and would 404. We use `anthropic/claude-sonnet-4.6`, the current Sonnet.

3. **Accepted minor behaviours:** a high-value overdue deal can appear in both priority calls and stale deals; uncontacted leads show all 15 most recent including no-name/no-phone records. Both are consistent with the brief.

## 10. Scaling Notes

The per-rep loop in Flow 01 is **sequential**, at roughly **45 seconds per rep**. The fixed 20-minute gap between Flow 01 (07:30) and Flow 02 (07:50) is comfortably safe up to about **25 reps**.

Beyond ~25 reps the run could overrun the 07:50 summary. Options at that point:

- **Trigger Flow 02 on Flow 01 completion** (instead of a fixed 07:50 schedule), with a later watchdog schedule as a backstop.
- **Parallelise the per-rep work**, or
- **Use the Anthropic Batch API** for the Claude generations to remove the per-rep serial bottleneck.

For the current team size, the existing fixed-schedule design is appropriate; revisit only as the Account Managers team grows past ~25.
